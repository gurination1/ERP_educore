**2. Exhaustive, Granular Breakdown of Technical Instructions & Requirements from Karanvir Sir:**

**Overall Architecture & Client Provisioning:**

1.  **Client-Specific URL**: Each client (school) will have its own unique URL (e.g., `bfgi.gurudotcom`, `sanawar.gurudotcom`, `dps.gurudotcom`).
2.  **Super Admin Dashboard**: As a Super Admin (the main user), logging into your central URL will open a dashboard displaying a list of all clients.
3.  **Client Creation Workflow**:
    *   Super Admin adds a new client's information (e.g., name) in their dashboard.
    *   A unique Client ID is generated.
    *   An option to "make functional" (Yes/No) will appear for the newly added client.
    *   If "Yes" is selected:
        *   A new, separate database (DB) is automatically created for this specific client (e.g., `db_clientid`).
        *   This new client DB is a replicated copy of a "Master DB" (or "Master Table" / "Master DB Client"). All default data, structures, and master tables from the Super Admin's master DB are copied to the client's new DB.
        *   A Super Admin (with full privileges) is automatically created for this client's specific DB.
        *   The Super Admin can reset the password for the client's admin from their central dashboard.
        *   A sub-domain is required for the client (e.g., `sanawar.gurudotcom`). This needs to be manually configured in the hosting provider's FTP and then linked from the Super Admin's panel.
4.  **Database Structure & Management**:
    *   **Master DB**: One primary Master DB for the entire organization (Super Admin).
    *   **Client DBs**: Multiple client-specific DBs, each a copy of the Master DB.
    *   **Naming Convention**: Client DBs will follow a convention like `DB_Client_ID` or `DB_Client_Name`.
    *   **Data Consistency**: The Master DB provides default tables and values (e.g., users, settings) that are copied to each new client DB.
    *   **Scalability/Migration**: The system should be designed to allow for future changes in the underlying database technology (e.g., migrating from MySQL to PostgreSQL) without requiring major code changes for data migration. Table structure should remain consistent.
5.  **Access & Permissions**:
    *   **Super Admin Access**: Super Admin can directly log in to any client's dashboard (bypassing the client's login page) from their central dashboard. This requires no separate login for the Super Admin for client dashboards.
    *   **Client Admin Access**: Client admins log in through their specific sub-domain URL.
    *   **User Roles**: Within each client's DB, there will be multiple user roles (Admin, Staff, Student) with different permissions.
    *   **Password Management**: Super Admin can reset passwords for client-level admins. Client-level admins can manage passwords for their own staff/students (subject to defined rights).
    *   **Activity Logs**: Super Admin can view all activity logs across all clients.
    *   **Security**: Implement lock mechanisms for past attendance/leave entries (e.g., 30/20/10 days limit).
6.  **Sub-domain & Hosting**:
    *   Each client gets a sub-domain (e.g., `clientname.gurudotcom`).
    *   This sub-domain needs to be manually set up in the hosting/FTP.
    *   The Super Admin panel will have linking functionality to associate the client's DB with their sub-domain and FTP.
    *   The client's admin portal (e.g., `admin.gurudotcom`) will be a separate URL from the client's public facing URL.
7.  **Mobile App Integration**:
    *   The core functionality and data structure should support mobile app integration.
    *   Two main app types: one for the Master Admin (or Super Admin) and one for clients/users.
    *   Apps will run in parallel with the web application, sharing the same DB APIs.
    *   Mobile apps need to be fully dynamic, fetching settings (payment gateways, UI elements, active/inactive features) from the backend.
    *   Mobile apps should support testing/live modes for payment gateways.

**Student & Course Management:**

1.  **Hierarchical Structure (Configurable)**:
    *   **Level 1**: School / Department / College (configurable by Super Admin in client's settings).
        *   Example: `College of Pharmacy`, `School of Humanities`.
    *   **Level 2**: Departments (within School/College) (always present).
        *   Example: `Department of Commerce`, `Department of Science`.
    *   **Level 3**: Courses (within Department).
        *   Example: `BA`, `B.Com`, `MA History`, `BSc Economics`.
    *   **Level 4**: Batches (within Course).
        *   Example: `BA Batch 2026-27`.
    *   **Level 5**: Sections (within Batch).
        *   Default: `Section A`. Can have multiple sections (B, C, D) if more students.
2.  **Course & Subject Configuration**:
    *   **Subject Types**: Compulsory, Elective, Extra (for non-graded activities).
    *   **Semester-wise Subject Assignment**: When a course is created (e.g., `BA`), all subjects for all its semesters (e.g., 6 semesters) should be defined upfront.
    *   **Subject Upload**: Option for Excel upload or a dynamic UI for bulk subject entry.
    *   **Subject Code Convention**: `Subject Name` + `Course Code` + `Semester Number` (e.g., `History_101_01` for History in BA, Semester 1).
        *   This allows clear identification and handling of subjects taught across different semesters or courses.
    *   **Subject Duplication**: Subject codes should not be duplicated within the same course. However, the same book (subject content) can be used across semesters with appropriate naming (e.g., `History_101_01` and `History_101_02`).
    *   **Subject-Course Mapping**: When creating a subject, specify which courses it can be offered in.
    *   **Exam/Report Card Control**: For each subject, there will be two checkboxes:
        *   "Take Exam": To indicate if an exam will be conducted for this subject.
        *   "Show Result in Report Card": To include the subject's result in the student's report card/DMC.
3.  **Batch & Semester Management**:
    *   **Annual/Semester System**: Each batch will be designated as either "Annual System" or "Semester System" (configurable).
    *   **Semester Control**: When a new batch is created, specify which semesters are applicable (e.g., if a 3-year MCA becomes 2 years, only 4 semesters will be selectable for new batches).
    *   **Start/End Dates**: Define start and end dates for each batch/semester.
4.  **Student Admission & Progression**:
    *   **Enquiry to Admission Workflow**:
        *   **Enquiry -> Registration Fee -> Admission Confirmation**:
            *   Students apply (enquiry).
            *   Student pays registration fee (configurable amount like ₹1000/₹3000/₹5000) against their enquiry number.
            *   Counsellor confirms admission.
            *   Upon admission, a unique Student ID (UID) is generated.
            *   The student's details move from "Enquiry" to "Student Register."
            *   Enquiry ID is linked to Student ID for historical tracking.
    *   **Student Profile Tabs**: Basic Details, Education Detail, Parent Detail, Occupation Detail, Career Choices, Fees, Documents (photo, marksheets), Facilities (Hostel, Transport, Food).
    *   **Fees Tab**: Shows enquiry fees, course fees per section/batch.
    *   **Dynamic Fees**: Fees (e.g., registration fee) are dynamic and based on course/semester configuration.
    *   **Extra Fees**: Option to add extra fees (e.g., ₹500) during the enquiry stage, which shows as "outstanding."
    *   **Refund Policy**: Each fee type will have a configurable refund policy (refundable/non-refundable).
    *   **Promote/Demote/Deactivate/Struck Off**: Student status management.
        *   "Promoted" implies moving to the next level/class/semester.
        *   "Demoted" implies repeating a year/semester due to failure.
        *   "Deactivated" (by HR for staff, similar logic for students leaving the institution).
        *   "Struck Off" (removed from active records).
        *   "Active" (currently enrolled).
    *   **Status Visibility**: In the student list, clearly display each student's current status.
5.  **Attendance & Time Table:**
    *   **Batch-wise Attendance**: Attendance is managed per batch. Group-wise attendance is explicitly ruled out to avoid complexity.
    *   **Subject Assignment to Students**:
        *   A matrix where students of a batch are listed horizontally and subjects vertically.
        *   Compulsory subjects selected during course creation will be auto-ticked.
        *   Elective/Extra subjects can be manually selected by the teacher/admin.
    *   **Teacher Subject Assignment**:
        *   A matrix where teachers are listed vertically and subjects horizontally (within a chosen course/batch).
        *   Teachers can be assigned multiple subjects.
        *   Each assignment can have a start and end date (or "full semester").
        *   This helps manage situations where teachers leave or multiple teachers teach the same subject over time.
        *   If a teacher leaves, their attendance-taking rights automatically cease after their last date. The new teacher takes over.
        *   The system should differentiate between active and inactive teachers when processing attendance.
    *   **Attendance-Taking Interface**:
        *   Teachers see "Mark Attendance" tab.
        *   Shows "Pending" attendance (past dates) and "Upcoming/Today's" attendance.
        *   Teacher selects date -> sees list of students for their assigned subjects in that batch -> marks P/A/L.
    *   **Attendance History**: Student attendance can be viewed by date range, full semester, monthly, weekly, or custom range.
    *   **Time Table**: The system will support creating time tables. When assigning a subject to a time slot, it checks if the assigned teacher is already assigned elsewhere or if the class is combined.
    *   **Combined Classes**:
        *   Option to mark a class as "combined" in the time table.
        *   If combined, it allows combining students from different sections/batches for the same subject/teacher.
        *   Prioritize attendance management based on the "primary" section/batch.
        *   The attendance interface for combined classes should allow the teacher to mark attendance for all relevant students from different sections in one go.
    *   **Attendance Lock**: Teacher/Student attendance entry is locked after a configurable number of days (e.g., 10, 20, 30 days) from the date of the class.

**Staff/Teacher Management (HR Integration):**

1.  **Staff Categories**: Teaching, Non-Teaching, Administration.
2.  **Designations**: Assign designations within each category.
3.  **Role Assignment**: Admin can assign multiple roles to a staff member (e.g., a non-teaching staff can also be a mentor in the entrepreneurship cell).
4.  **Basic HR Details**: Personal info, education, etc.
5.  **Document Upload**: Mandatory document uploads (experience letter, previous pay slips, living letter, etc.).
    *   **Configurable Mandatory Fields**: Admin can mark specific documents as mandatory.
6.  **Salary & Payroll**:
    *   **Basic Structure**: Basic HR, Total Net Salary.
    *   **TDS**: Configurable TDS percentage.
    *   **PF/ESI**: Configurable PF/ESI (Provident Fund/Employee State Insurance).
        *   `PF Apply` / `ESI Apply` checkboxes in employee settings.
        *   Rules for PF (e.g., mandatory for salary up to ₹15000) and ESI (e.g., up to ₹20000, may depend on 20+ employees). These rules should be dynamic and configurable.
        *   `Voluntary PF`: Option for employees to opt-in even if salary is above mandatory threshold.
    *   **Security Deduction**: A separate tab for security deductions.
        *   Amount, start month, end month for deductions.
        *   Auto-fill functionality for break-up.
        *   Once fully deducted, the field should be locked.
    *   **NOC & Refund**: Link security deductions to NOC (No Objection Certificate) status.
        *   If all required NOCs are complete, "Security Release" button becomes active.
        *   Record payment mode/details for security refund.
        *   This creates an online NOC system for staff leaving.
7.  **Access Control (Granular)**:
    *   A comprehensive panel for controlling information visibility and edit permissions for staff and student data.
    *   **Field-Level Permissions**: For every field in staff/student information:
        *   `View`: Can staff/student view this field?
        *   `Edit`: Can staff/student edit this field?
    *   **Role-Based Access**: These permissions will be assigned to different staff roles (Teaching, Non-Teaching, Admin).
    *   **Admin Override**: Admin will always have full view/edit access.
    *   **View vs. Edit Hierarchy**: If "View" is disabled, "Edit" should be automatically disabled (and hidden/grayed out).

**General System Requirements:**

1.  **Dynamic UI**: The system should be highly dynamic, allowing for backend configuration to change front-end behavior (e.g., payment gateways, app features).
2.  **Reporting**: Generate reports based on all data points (e.g., combined classes, subject assignments, teacher workload, student status).
3.  **Unified Control**: Super Admin has a single point of control for managing all clients, their settings, and basic provisioning.

**Database & Application Design Considerations:**

1.  **DB Agnostic Approach**: Design the database model/architecture to be easily migratable between different database systems (e.g., MySQL, PostgreSQL) in the future.
2.  **API-First Approach**: Build robust APIs to serve both web and mobile applications consistently.
3.  **Code Naming Conventions**: Use clear and consistent naming conventions for all codes (subjects, courses, etc.) to ensure easy understanding and avoid conflicts.
4.  **Error Handling**: Implement robust error handling for conflicting schedules (e.g., a teacher assigned to two classes simultaneously).
5.  **Frontend Frameworks**: React for web app, Flutter for mobile app (recommended for cross-platform compatibility).
