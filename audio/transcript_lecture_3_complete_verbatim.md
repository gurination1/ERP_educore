**2. DETAILED ARCHITECTURAL & LOGICAL DECONSTRUCTION:**

**A. Core System Design & Data Management:**

1.  **Combined Classes Logic:**
    *   **Problem:** When multiple classes (e.g., BA and B.Com) have the same subjects taught by the same teacher, they are combined.
    *   **Requirement:** The system must handle combined classes for both compulsory and elective subjects.
    *   **Edge Case (Elective):** If an elective subject is combined, students from different classes might be in the same combined class.
    *   **Edge Case (Attendance):** If a student from Class A takes a combined elective with Class B, their attendance for that specific subject/period should be recorded correctly for Class A.
    *   **Edge Case (Splitting Classes):** If students from a single class (e.g., Class A) are split across multiple combined elective classes (e.g., some in Combined Class 1, some in Combined Class 2, some free), the system must track this. A single class can be split into 2-3 parts within one period.
    *   **Solution Concept:** For a single period in a timetable, if multiple electives are chosen by students from the same class, it results in multiple "combined classes" (e.g., CC1, CC2, CC3, CC4).
    *   **"Free Period" Concept:** If a student doesn't choose any elective for a specific period, they are considered in a "Free Period" combined class (e.g., CC4 for a free student).
    *   **Attendance for Free Period:** Attendance for "Free Period" will be marked as "FC" (Free Class) and will count as "Present" but won't be tied to a specific subject. By default, attendance will not be marked for free periods.

2.  **Reporting Requirements:**
    *   Generate reports for:
        *   Number of combined classes.
        *   Number of subjects.
        *   Number of teachers.
        *   Subjects assigned to each teacher.
    *   Reports need to be generated at every level (e.g., school, department, course, class).

3.  **Time Table Generation:**
    *   **Process:** First, understand subjects and classes, then understand different cases (compulsory vs. elective, combined vs. single).
    *   **Logic:**
        *   If one teacher teaches one class for a subject, it's straightforward.
        *   Complexity arises when students from different classes attend a single class (combined classes).
        *   Attendance for combined classes needs careful handling (e.g., a student from Class A attending a combined class with Class B should have attendance recorded for Class A).

4.  **Mapping Matrix (Overall Structure):**
    *   **Matrix 1: School/Department to Course Mapping:**
        *   Assign courses to schools (e.g., School of Humanities).
        *   Assign courses to departments (e.g., Department of History within School of Humanities).
        *   **Edge Case (No Department):** If a school has no specific departments, the department name can be the same as the school name (e.g., Department of Humanities).
        *   **Filtering:** This structure helps in filtering courses by school/department.
        *   **Example:** BA in Humanities, MA in History. MA History would go under Department of History, while BA would go under Department of Humanities (if no specific BA department). All courses would still be under School of Humanities.
        *   **Code:** Each school/department/course will have a unique code.

    *   **Matrix 2: Batch/Session Creation:**
        *   Create a "session" (e.g., 2026-2029 for a 3-year course). This represents the entire duration of a course for a specific intake year.
        *   **Future-proofing:** Allow adding future sessions.
        *   **Time-line:** Define time-lines for each session (e.g., start/end dates).
        *   **Visibility:** Use checkboxes to control session visibility.
        *   **Hierarchy:** Course -> Session -> Semesters.
        *   **Subject Assignment:** Assign subjects to semesters within a session.
        *   **New Subjects:** Allow adding new subjects to the master list and then assigning them to relevant sessions/semesters.

    *   **Matrix 3: Teacher Mapping:**
        *   Map teachers to courses first, then to specific subjects within those courses.

    *   **Matrix 4: Student Mapping:**
        *   Map students to subjects within their respective classes/semesters.

    *   **Overall Mapping Process:** This entire mapping process involves 5-6 steps. The goal is to eventually automate these steps.

**B. Database Architecture & Scalability:**

1.  **Database Migratability:**
    *   **Requirement:** The database model/architecture must be migratable.
    *   **Future-proofing:** The choice of DB (MariaDB, MySQL, MS SQL, SQLite, PostgreSQL) should be flexible and decided at the time of production deployment.
    *   **Impact:** This means the core table structure should remain consistent, allowing easy migration between different DB systems.

2.  **Multi-Client/Multi-Tenant Architecture:**
    *   **Master Panel (Super Admin):**
        *   Super Admin can add "Entities" (clients/schools).
        *   Manage admin passwords for each entity.
        *   Login directly into an entity's panel from the Super Admin panel.
        *   Manage entity subscriptions.
        *   **"Go in Production" Feature:** A button/checkbox to mark an entity as "in production."
            *   Upon activation, an automatic DB will be created for that entity.
            *   Login, dashboard, and default settings will be live.
            *   Existing student/inquiry data (if any) will be transferred to the new production DB.
    *   **Master DB / Sample Client DB:**
        *   Maintain a "master DB" or "sample client DB" (dump DB).
        *   When a new client goes live, this sample DB will be replicated for them.
        *   Each client will have their own dedicated DB.
    *   **Client Management:**
        *   Super Admin manages client-specific FTP, subdomains, etc.
        *   **Subdomain Management:** Subdomains cannot be managed purely via code. They must be manually created on the hosting provider, and then the IP/details are set within the EduCore panel.
        *   **Unique Codes:** Use unique codes (e.g., based on City/State) for each client. This code will be crucial for generating FTP addresses, other unique identifiers, and login IDs.

**C. Mobile App Development (Dynamic Approach):**

1.  **Dynamic Mobile App:**
    *   **Goal:** The mobile app should be fully dynamic, requiring no code changes for updates.
    *   **Payment Gateways:**
        *   Schools can have multiple payment gateways.
        *   Manage payment gateways from the master panel (add/remove any number).
        *   Select the default/active payment gateway from the master panel.
        *   The mobile app will dynamically pick the active payment gateway.
        *   **Hardcoding Issue:** Avoid hardcoding payment gateway details in the app (a problem observed in EduMarshal).
        *   **Example (EduMarshal):** Pharmacy and Law schools had different current accounts and payment gateways, but their app was hardcoded to one, causing issues.
        *   **Payment Mode (Live/Test):** Implement a "Payment Mode" setting (Live/Test).
            *   If in "Test Mode," the payment button should not be visible to students.
            *   Allow specific IDs to be enabled for testing in test mode.
            *   If in "Live Mode," it's live for everyone.
        *   **Dynamic API Keys:** All API keys for payment gateways should be dynamic, fetched from the backend.
        *   **Run-time Behavior:** The app should check the live/test status at run-time and adjust its behavior (e.g., show/hide payment options).
    *   **Development Platform:**
        *   The client can choose the development platform (React Native or Flutter).
        *   **Recommendation:** Flutter is preferred for high-end financial products due to better iOS compatibility and design, but React Native is acceptable for this software.
        *   **Unified Development:** Ideally, the web app and mobile app should be developed on the same platform/framework to maintain consistency and avoid separate development efforts for different levels (e.g., not building web in Laravel and mobile in React/Flutter/Swift/Android Studio separately).
        *   **Mobile View Settings:** What is visible on mobile should be configurable via backend settings.

**D. Staff/HR Module:**

1.  **Staff Addition & Categorization:**
    *   **HR Module:** Create a dedicated HR module.
    *   **Staff Levels:** Categorize staff into three levels:
        *   Teaching
        *   Non-Teaching
        *   Administration
    *   **Designation:** Each staff member will have a designation.

2.  **Additional Roles (Multi-Role Support):**
    *   **Tab:** Create an "Additional Role" tab for staff.
    *   **Information:** Store information about which school, department, and designation the additional role pertains to.
    *   **Selection:** Allow single or multi-select for roles.
    *   **Example:** A non-teaching staff member might also be taking competitive classes in the School of Humanities (BA) and be a mentor in the Entrepreneurship Cell (multi-role). Or a teaching staff member might teach in two different schools.
    *   **Multi-Banks:** Allow adding multiple bank accounts for a staff member, with a default option.

3.  **Education & Documents:**
    *   **Qualification:** One qualification must be marked as "Last" (highest).
    *   **Resume:** Resume upload is mandatory.
    *   **Documents:** Upload various documents: previous payslips, experience letters, relieving letters.
    *   **Compulsory Documents:** Admin should be able to mark which documents are compulsory for staff.

4.  **Salary Details & Deductions:**
    *   **Salary Structure:** Basic salary, HRA, total net salary.
    *   **TDS:** TDS percentage.
    *   **PF/ESI Settings:**
        *   Enable/disable PF (Provident Fund) and ESI (Employee State Insurance) from settings.
        *   **Rules:** PF rules (e.g., for salaries up to 15,000 INR), ESI rules (e.g., for salaries up to 20,000 INR, and potentially for 20+ employees). These rules need to be dynamic and state-specific.
        *   **Employee-level Application:** When viewing an employee's profile, there should be settings to apply PF/ESI (e.g., "PF Apply," "ESI Apply").
        *   **Voluntary PF:** Allow voluntary PF contributions even if salary exceeds the threshold (e.g., 40,000 INR salary, but employee wants to contribute).
        *   **Dynamic Enable/Disable:** Each PF/ESI option should be individually enable/disable-able for each employee.
    *   **Security Deduction:**
        *   **Tab:** Create a dedicated tab for "Security Deduction."
        *   **Details:** Amount of security deduction, start month, end month for deduction from salary.
        *   **Breakup:** Automatic breakup of deductions over months.
        *   **Manual Adjustment:** Allow manual adjustment of random deductions.
        *   **Total Match:** The total deducted amount must match the security amount.
    *   **Salary Information Tab:**
        *   Connects to salary payment.
        *   When salary is paid, information is stored in this table.
        *   If security has been deducted, the security field will be locked.
    *   **NOC (No Objection Certificate) & Security Release:**
        *   When an employee leaves, connect security refund to NOCs.
        *   If all required NOCs are cleared/selected, the "Security Release" button will be enabled.
        *   Record payment mode and upload proof for security release.
        *   This is a complex HR system feature not commonly found.

**E. User Permissions & Views:**

1.  **Information Visibility & Editability (Checkboxes):**
    *   Create a comprehensive checkbox panel for both Student Information and Staff Information.
    *   **Fields:** All fields within these sections will be listed.
    *   **Admin View:** Admin will have all fields checked (full view/edit).
    *   **Staff View:**
        *   "View" checkbox: Show/hide information to staff.
        *   "Edit" checkbox: Allow/disallow staff to edit information.
        *   **Dependency:** Edit functionality only works if "View" is enabled.
    *   **Student View:** Similar logic for students (which fields they can view/edit).

**F. Automation (Future Scope):**

1.  **Automation of Mapping Steps:**
    *   After the initial manual mapping (5-6 steps for courses, batches, teachers, students) is complete, identify steps that can be automated.
    *   **Goal:** Certain steps should trigger automatically based on specific events (e.g., creating a new batch automatically aligns certain mappings).

**G. Other Notes:**

*   **Exam, Weightage, Event:** These features are to be discussed later. Focus on normal subject and attendance first.
*   **Fees:** Student security and fees will be handled later, after the batch module is clear.
*   **Software Quality:** The goal is to build a software that is "best" compared to existing solutions like EduMarshal.
*   **Server Capacity:** Consider how many databases a single server can handle (technical question for Guri to research).
*   **Project Development:** The project will be built iteratively. The current focus is on getting the core structure right.
