#### 2. Module Specifications & UI Rules

##### A. Faculty HRMS & Role-Based Access Control (RBAC)
*   **Navigation:** Settings $\rightarrow$ Faculty HRMS $\rightarrow$ Roles / Role Assignment.
*   **UI Rules for Roles:**
    *   **Admin View:** Sees complete permission matrices across the system, enabling granular role assignment and bulk updates.
    *   **Employee/User View:** Accessing an employee profile displays their assigned roles dynamically.
    *   **Bulk Operations:** Support for bulk selection/assignment of roles (e.g., granting "Fee Collection" privileges across multiple accounts) with a dedicated **Revoke** button to strip selected IDs of specific access parameters.
*   **Default Rights Automation:**
    *   **Teaching vs. Non-Teaching Staff:** Dedicated configuration pages mapping default rights based on staff classification.
    *   **Designation-Based Inheritance:** Roles inherit dynamically based on designations (e.g., HOD profiles inherit specific teaching-plus-management reporting capabilities). Clicking a role instantly opens its rights configuration matrix with tick-box toggles that auto-apply changes globally.

##### B. Institutional Governance & Master Data Tables
*   **Master Table Implementation Rule:** 
    *   Hardcoded categories/lists (Departments, Designations, Categories) must be completely eliminated in favor of dynamic Master Tables managed via Super Admin / Admin panels.
    *   **Location:** Every functional module/setting page must feature a designated link/button to its corresponding **Master Table / Master Data / Master Information** panel.
*   **Deletion Safety Rule:** Master records *cannot* be deleted if they are currently assigned or referenced anywhere within active software transactions. Deletion is only permitted if unlinked/unassigned.
*   **Multi-tenant / Campus Architecture:** Multi-campus structure controls must seamlessly inherit configuration states without throwing impersonation/tenant mapping errors (addressing Supabase/database migration bugs noted in the session).

##### C. Student Promotion & Demotion Engine
*   **Promotion Module:** Setup workflows allowing bulk promotion of students to subsequent semesters/academic years for upcoming sessions.
*   **Demotion Module Specifications:** When demoting a student to a prior academic term, the system must trigger a decision matrix prompt handling historical records and financial liabilities:
    1.  **Journey History Option A (Complete History Preserved):** Maintains full tracking (e.g., student reached 5th semester, demoted back to 3rd semester), rendering the complete timeline visible on administrative dashboards.
    2.  **Journey History Option B (Restart/Inactivation):** Restarts tracking strictly from the target demoted semester (e.g., 3rd semester). Semesters 4 and 5 are marked invisible/inactive in standard staff views while remaining accessible via Admin audit logs.
*   **Financial & Fee Adjustments on Demotion:**
    *   The system cross-analyzes financial ledgers across historical terms (paid amounts, pending balances, fee structures of the target demoted semester).
    *   **Null and Void Check:** Admin/Accountant interface prompts whether pending/paid fees from skipped/advanced semesters should be nulled out, voided, or carried forward as adjustments against the target semester's fee ledger.
    *   **Approval Workflow:** Demotion requests initiated by faculty/staff require explicit approval flags from Admin/Accountant roles before committing ledger recalculations.
