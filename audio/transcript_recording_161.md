## Detailed Requirements and Architectural Decisions:

**1. Partner Portal:**
*   **Menu Item:** Create an "Account" menu item.
*   **Functionality:** Within the Account menu, implement a "Partner Add" feature.
*   **Partner Details:**
    *   **Partner Type:** Field to specify the type of partner (e.g., "Sole Proprietor").
    *   **Partner Name:** Field for the partner's firm name.
    *   **Contact Details:**
        *   Multi-valued: Allow multiple contact details per partner.
        *   Default: One contact detail must be marked as default.
    *   **Bank Details:**
        *   Multi-valued: Allow multiple bank accounts per partner.
        *   Default: One bank account must be marked as default.
    *   **Taxation Details:**
        *   Include fields for PAN number, GST number, and other relevant tax information.
*   **Contact Person:**
    *   Multi-valued: Allow multiple contact persons per partner.
    *   Default: One contact person must be marked as default.
*   **Logging:**
    *   Log all partner additions: Who added, what was added, when it was added, with a timestamp.

**2. Admissions CRM / Pre-Admission / Enquiry Stage:**
*   **Enquiry Form (Basic Information):**
    *   Name (Student's).
    *   Gender (Male/Female).
    *   Father's Name.
    *   Mobile Number.
    *   Email Address.
*   **Course Details:**
    *   After basic info, allow selection of courses.
    *   Display associated fees and duration for the selected course.
*   **Workflow:**
    *   Student confirms interest in a course.
    *   **Remarks:** Implement a system to save remarks at every stage of the enquiry process.
    *   **Payment Module Integration:**
        *   Upon confirmation, redirect to a payment module.
        *   This payment module should be the *same* as the existing "Fees Collection" module.
        *   Allow selection of the fee type (e.g., "Registration Fee").
        *   Automatically populate the fee amount based on the selected course.
        *   Process payment.
        *   Generate and provide a receipt (print option).
*   **Profile Update/Admission:**
    *   After payment, the student's profile should be updated to "Admitted" or "Student".
*   **Counselor Functionality:**
    *   **Enquiry Management:** Counselors can view enquiries.
    *   **Remarks Tree:** Counselors can add remarks to each enquiry. These remarks should form a "tree" or log, showing all interactions (calls, follow-ups, etc.).
    *   **Admission Probability:**
        *   A field for "Admission Probability" (e.g., percentage out of 100 or 10).
        *   Counselors will update this probability.
    *   **Telephony Integration (Dialer):**
        *   **Option:** Manual calling or integrated dialer.
        *   **Admin Control:** The dialer feature should be configurable (enable/disable) in the admin panel.
        *   **API Integration:** If enabled, it requires API integration with a calling service.
        *   **Workflow (with dialer):**
            *   Counselor clicks to call a student's number.
            *   Automatic dialing via internet (headset connected).
            *   Call recording is automatically saved.
            *   Counselor fills in call details (what was discussed) and updates admission probability.
            *   Save button to log the call and updates.
        *   **Recommended Services:**
            *   message94.com (good for dialer, SMS, WhatsApp, Email).
            *   Twilio (commonly used).
            *   Exotel (user has experience, offers free credits for demo).

**3. Data Upload (Bulk Data Import):**
*   **File Types:** Support CSV or Excel file uploads.
*   **Format Flexibility:** The uploaded file should *not* require a specific format; only column headings are necessary.
*   **Mapping Interface:**
    *   Upon upload, display a window for field mapping.
    *   Left side: List of system fields (e.g., "Student Name", "Father Name").
    *   Right side: Dropdown menus for each system field, populated with the column headings from the uploaded Excel/CSV file.
    *   User maps uploaded columns to system fields (e.g., map "Name" from Excel to "Student Name" in the system).
*   **Data Validation and Preview:**
    *   After mapping, display a preview of the data.
    *   Categorize data entries with statuses:
        *   **Fresh:** New, valid data.
        *   **Probable Duplicate:** Data that might match existing records (e.g., same name, similar mobile).
        *   **Wrong Data:** Data failing validation checks (e.g., incomplete mobile number, invalid Aadhar number, other custom checks).
    *   **Correction Option:** Provide an option to download an Excel file containing only "Probable Duplicate" and "Wrong Data" entries, so the user can correct them and re-upload.
*   **Import Functionality:**
    *   A final "Import" button.
    *   This button should *only* import "Fresh" data into the system.
*   **Destination:** Imported data (Fresh) goes into the "Enquiry" stage.
*   **Logging:**
    *   Log all bulk data uploads: Who uploaded, what file, when, and the source of the Excel (if applicable).

**4. Student Conversion Workflow:**
*   **Enquiry to Student:** When an enquiry pays the fees (via the payment module), their status changes from "Enquiry" to "Admission" or "Student".
*   **Unique ID:** The student should receive a unique ID (UID) upon admission.
*   **Data Movement:** The student's data should be moved or linked to a "Student" table.
*   **Counselor View:** Once converted to a student, the entry should no longer appear in the counselor's "Enquiry" list. It should appear in a separate "Student Panel".
*   **Database Status:** The ERP status for this entry will change from "Enquiry" to "Admission".

**5. Reporting and Analytics:**
*   **Report Section:** Create a dedicated report section.
*   **Enquiry Stage Reports:** Reports showing the number of enquiries at each stage.
*   **Analytics Corner:** A section for general analytics.

**6. General Architectural / Database Decisions:**
*   **Database First:** Emphasize that the database structure is paramount and should be robust, as the UI can change frequently.
*   **Database Stability:** The database schema should be designed to avoid frequent changes.
*   **Future-Proofing:** Every database table should include at least five extra, unused fields. These fields should not be visible by default but can be made visible if needed in the future.
*   **Master Tables:** Use master tables for statuses (e.g., "Enquiry", "Admission").
*   **Logging (Comprehensive):** All significant actions (partner add, data upload, user actions, rights management) must be logged with details like who performed the action, what the action was, and a timestamp.

**7. User Management and Rights:**
*   **Logging:** User management and rights management actions should also be logged.
*   **User Login:** User login events should be logged.

**8. UI/UX Specifics:**
*   **Table Form for Updates:** If updates are allowed for data (e.g., in the data preview stage), it should be presented in a table format for easy editing.
*   **Clear Status Indicators:** Use clear visual indicators for "Fresh", "Probable Duplicate", and "Wrong Data" during bulk upload preview.

**Summary of Key Instructions:**
*   Build a comprehensive Partner management system with multi-valued contact/bank details and taxation.
*   Develop an Admissions CRM starting from an enquiry stage, integrating with a payment module and allowing counselors to manage leads with remarks, probability, and optional dialer integration.
*   Implement a flexible bulk data upload feature with intelligent mapping, validation (fresh, probable duplicate, wrong data), and selective import.
*   Ensure robust logging for all critical actions and data changes.
*   Prioritize a stable database design over UI, including future-proofing with extra fields.
*   Integrate with external calling/SMS/email APIs (message94.com, Twilio, Exotel).
*   Ensure smooth transition from enquiry to student status upon fee payment, with appropriate data handling and UI changes.
